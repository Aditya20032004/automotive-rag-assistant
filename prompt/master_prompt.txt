## 2B. LOCKED TECH STACK AND HARDWARE CONSTRAINTS (do not deviate without flagging it explicitly)

**My hardware**: laptop RTX 4050, 6GB VRAM. Every choice below must actually run within this budget. If you ever suggest something that risks exceeding it, you must say so explicitly before suggesting it, not after I hit an OOM error.

- **Orchestration framework**: `llama-index`, not `langchain`. Phase 1 is a pure RAG pipeline (ingest → retrieve → answer from context) with no agentic/multi-tool behavior, and llama-index is the more direct, purpose-built tool for that — use it consistently across all code in this project, do not mix in langchain components.
- **LLM inference runtime**: **Ollama running a GGUF-quantized model** — not raw `transformers` + `bitsandbytes`. GGUF (via `llama.cpp` under the hood) is more memory-efficient on small VRAM budgets and supports partial GPU/CPU offload, which raw `transformers` quantization does not handle as gracefully at this VRAM size.
- **Default base model for Phase 1**: **Phi-3-mini (3.8B), Q4 GGUF, via Ollama.** At ~2.2-2.5GB VRAM, this leaves comfortable headroom on a 6GB card for context window plus the embedding model running alongside it.
- **Documented fallback**: **Mistral 7B, Q4_K_M GGUF, via Ollama** — usable on 6GB but tight, with little headroom. Only recommend switching to this after Phase 1 is validated on Phi-3-mini and if answer quality genuinely needs the bump. Flag the tighter memory margin explicitly if I ask to switch.
- **Do not suggest**: LLaMA 3 8B or Mistral 7B via raw `transformers`/`bitsandbytes` as the primary path (too tight for 6GB with no offload flexibility), or any model above ~8B parameters for local Phase 1 work.
- **Embedding model**: small `sentence-transformers` model (e.g. `all-MiniLM-L6-v2`) — under 500MB, runs comfortably alongside the LLM on the same 6GB card without contention.
- **Vector store**: Chroma (local, CPU-only, no VRAM impact) — no change from earlier guidance, just re-confirming it doesn't compete for VRAM.
- **OOM-prevention tuning (build these into the pipeline, not as an afterthought)**:
 - Chunk size: 500-800 tokens (not larger) — chunking is what keeps context manageable, it is not itself a memory risk and must not be removed or skipped to "save memory."
 - Retrieval top-k: 3-5 chunks per query (not 10+), to keep total context fed to the model bounded.
 - Batch the embedding step during indexing (batches of 32-64 chunks), rather than embedding the entire corpus in one call.
- **Phase 2 & 3 compute**: explicitly out of reach on this laptop. Phase 2 (LoRA) needs ~16-24GB VRAM even with quantization — plan for **Google Colab (free T4, 16GB)** or **Kaggle Notebooks (free T4/P100)**. Phase 3 (DAPT) needs multi-GPU/cloud regardless — do not present either as locally runnable on this hardware.
